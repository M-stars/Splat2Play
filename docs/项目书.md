## 1. 项目背景与定位

### 1.1 背景

3D Gaussian Splatting(3DGS, Kerbl et al., SIGGRAPH 2023)用数百万个带颜色和不透明度的椭球体(高斯)显式表示一个场景,数小时采集即可获得照片级真实感。游戏工业最大的成本是内容成本:照片级真实街区手工制作需要数周到数月的美术工时,而 3DGS 是一次数小时的采集。

### 1.2 核心矛盾(项目要解决的问题)

游戏引擎的一切游戏系统都建立在**网格(mesh)世界观**上:碰撞、寻路、光照、剔除、流送。而 splat 资产:
- 没有拓扑和网格 → 无法直接生成碰撞体和 NavMesh;
- 不写深度、外观烘焙在 SH 里 → 无法正确参与动态光照与阴影;
- 是整体渲染的 → 无法像网格资产那样做 LOD、流送、遮挡剔除。

业界已有实践(2026):XGRIDS 在 Unreal、PlayCanvas 在浏览器做出了"扫描场景变可玩关卡"的完整管线;**Unity 侧没有成型工具链**——这就是本项目的定位。

### 1.3 目标交付物

| 交付物 | 说明 |
|---|---|
| 可玩 Demo | 第一人称微型关卡:碰撞、手电筒近似影子、AI 追击、雾效融合、流送 60fps |
| Unity 工具链 | 编辑器内一键"扫描资产 → 游戏就绪关卡"的烘焙管线 |
| 技术博客 | 以"近似动态光照"为主题的深度文章(求职展示) |
| 性能报告 | `docs/benchmarks.md`,含各阶段量化数据 |

### 1.4 明确不做的事(v0 范围外)

- 不做移动端/Web/主机适配(桌面 DX12 优先);
- 不做内置管线/HDRP 支持(URP only);
- 不做角色绑骨/动画(另一个方向,不在本项目范围);
- 不做重训练式 relighting(学术路线,本项目用运行时近似)。

## 2. 术语与技术基础(自包含,不依赖外部资料)

### 2.1 3DGS 数据模型

一个 3DGS 资产由 N 个高斯组成,每个高斯(splat)的参数:

| 参数 | 维度 | 含义 |
|---|---|---|
| position | float3 | 椭球中心 |
| scale | float3 | 三个主轴半径(σx, σy, σz) |
| rotation | quaternion(4) | 椭球朝向 |
| opacity | float | 不透明度(经 sigmoid 变换) |
| color/SH | float3 + 球谐系数 | 0 阶为基色,SH1/2/3 分别 +9/+24/+45 个系数,产生视角相关外观 |

标准二进制 PLY 格式:每 splat 62 个 float 属性(x y z nx ny nz f_dc(3) f_rest(45) opacity scale(3) rot(4))。渲染内存约 28B/splat(无 SH)至 60B/splat(SH3)。

### 2.2 3DGS 渲染流程

每帧:① 遍历 splat,按视锥剔除 → ② 将 3D 高斯投影为 2D 协方差 → ③ 按深度排序(通常 GPU Radix Sort)→ ④ 按 alpha 混合从前到后/从后到前绘制。**关键性质:排序每帧重做,所以 splat 位置被外部修改后无需手动重排;但视锥剔除用的包围盒是预计算的,移动 splat 后必须更新。**

### 2.3 本项目依赖的渲染器

[aras-p/UnityGaussianSplatting](https://github.com/aras-p/UnityGaussianSplatting)(MIT,包名 `com.unity.gaussian-splatting`):事实上的 Unity 3DGS 渲染器。
- 内部结构:资产按 chunk 划分(每 chunk 约 65535 个 splat,chunk 有独立包围盒用于剔除与排序截断);GPU 侧使用 ComputeShader 排序与渲染;支持内置管线/URP/HDRP(URP 需 Unity 6);图形 API 支持 D3D12/Metal/Vulkan,不支持 GLES/WebGPU。
- 核心类型:`GaussianSplatAsset`(资产)、`GaussianSplatRenderer`(渲染组件)、cutout 裁剪工具、编辑器创建菜单。
- 维护状态:进入维护模式(v1.1.2,2026-10),接口稳定,适合作为基座。

### 2.4 本项目用到的其他技术

| 技术 | 用途 | 最小知识 |
|---|---|---|
| 体素化(voxelization) | 把 splat 集合变成规则网格上的密度场 | 三维网格 + 密度累加 |
| 洪泛填充(flood fill) | 区分封闭体的内外 | 6-连通 BFS,从网格边界种子点扩散 |
| SDF(有向距离场) | 二值体素 → 平滑距离场 | 欧氏距离变换;可选 JFA(Jump Flooding)算法 |
| Surface Nets / Marching Cubes | SDF/二值场 → 三角网格 | Surface Nets 推荐:实现简单、平滑、约 100 行 |
| NavMesh | 寻路 | `com.unity.ai.navigation` 的 NavMeshSurface 组件烘焙 |
| depth-only pass | 只写深度不写颜色的渲染 | ShaderLab:`ColorMask 0` + `ZWrite On` |
| shadow map | 阴影 | URP 主光源阴影:`_MainLightShadowmapTexture`,采样宏 `SampleShadowmap` |
| Burst Job | 编辑器端 CPU 并行计算 | `IJob`/`IJobParallelFor` + NativeArray |
| Render Graph / ScriptableRenderPass | URP 自定义渲染 pass | Unity 6 URP 的 RenderGraph API |

## 5. 模块规格

> 每个模块按统一模板:目标 → 输入/输出 → 算法步骤 → 参数 → 接口 → 边界情况 → 验收标准 → 降级方案。

### 5.1 模块 M1:碰撞代理生成(核心模块一)

**目标:** 输入 `GaussianSplatAsset`,输出可用于 `MeshCollider` 的封闭三角网格,使玩家不穿墙、不掉地。

**输入/输出**

- 输入:`GaussianSplatAsset`(每 splat:position/scale/rotation/opacity)、烘焙设置 `ProxyBakeSettings`
- 输出:`ProxyData`(ScriptableObject):代理 `Mesh`(含顶点/三角形)、场景 AABB、体素参数记录、可选 SDF 体素场(供 M4 剔除复用)

**算法步骤(编辑器内,一次性)**

1. **位置提取**:从 `GaussianSplatAsset` 读取每 splat 的 position/scale/rot/opacity。优先使用资产的 GPU buffer 读回(`ComputeBuffer.GetData`,编辑器端可接受);若 API 不足,直接解析源 PLY(binary_little_endian,每 splat 62 float,属性布局见 §2.1)。N 百万级时读回约 28MB 内存,可接受。
2. **场景包围盒**:所有 splat 位置的 AABB 外扩 0.5m,作为体素网格范围。
3. **密度场体素化**(compute shader 或 Burst):分辨率 R 默认 256³(可调 64–512)。每个 splat 向其椭球 AABB 覆盖的体素累加:`density[v] += opacity * exp(-dist²/(2σ²))`,dist 为体素中心到椭球中心在椭球局部坐标下的归一化距离,σ 由 scale 给出。
4. **二值化**:`density[v] ≥ threshold`(默认 0.5,可调)→ 实体。
5. **洪泛填充**:从网格最外层找密度 < threshold 的体素作种子,6-连通 BFS 扩散标记"外部";未标记的"非实体"体素并入实体。**这一步把开放扫描中的封闭体(房屋、车内)识别出来**。
6. **SDF(可选但推荐)**:对二值场做欧氏距离变换(JFA 在 compute shader 上实现),得到符号距离场,让网格提取更平滑。
7. **网格提取**:Surface Nets(推荐,代码量小、平滑)或经典 Marching Cubes(256 case 表,可用公开 MIT 表数据,需在提交中注明来源)。输出三角网格。
8. **抽稀**:顶点聚类合并(以体素尺寸为聚类半径,天然对齐);目标:代理网格面数 ≤ 15 万三角形(超过则增大体素或聚类半径重跑)。
9. **装配**:生成 `MeshCollider`(Convex 关闭;若需物理刚体交互的区域,允许在向导中手动框选生成盒体)→ 与 `GaussianSplatRenderer` 一起装配成 `SplatLevel` prefab。

**参数表(`ProxyBakeSettings`,ScriptableObject 持久化)**

| 参数 | 默认 | 说明 |
|---|---|---|
| voxelResolution | 256 | 每轴体素数,上限 512 |
| densityThreshold | 0.5 | 二值化阈值 |
| fillInterior | true | 是否洪泛填充封闭内部 |
| useSDF | true | 平滑提取 |
| maxTriangles | 150000 | 抽稀目标上限 |
| boundsMargin | 0.5m | AABB 外扩 |

**接口签名(C#,实现必须一致)**

```csharp
namespace Splat2Play.Proxy
{
    public sealed class ProxyBakeSettings : ScriptableObject { /* 参数表字段 */ }

    public static class SplatProxyBaker
    {
        // 同步烘焙(编辑器). 进度回调用于向导窗口.
        public static ProxyData Bake(GaussianSplatAsset asset,
                                     ProxyBakeSettings settings,
                                     Action<string, float> onProgress = null);
    }

    public sealed class ProxyData : ScriptableObject
    {
        public Mesh CollisionMesh;      // 只读使用
        public Bounds SceneBounds;

        public ProxyBakeSettings Settings; // 复现参数
    }

```

**边界情况(必须处理并在文档记录)**

- 细长结构(栅栏、灯杆):低于体素分辨率会被抹掉 → 参数上提高局部分辨率不可行时,提供"补丁盒体"手动列表(编辑器向导里画 box collider)写入 ProxyData;
- 开放场景(天空、远景):洪泛填充会把无封闭的空旷区当外部 → 允许在向导中指定"封闭区域"包围盒列表,只对内部做填充;
- 悬浮噪点(扫描常见漂浮 splats):密度阈值天然过滤;残余用"移除 AABB"工具手动排除;
- 内存:512³ float 场约 512MB → 512 档强制要求 useSDF=false 且提示用户;默认 256³(float,64MB)安全。

**验收标准**

- [ ] 扫描街角场景,玩家胶囊体(CharacterController)连续行走 60 秒,无穿墙、无坠地;
- [ ] 中等场景烘焙 ≤1 分钟(RTX 级),内存峰值 <2GB;
- [ ] 同参数重跑烘焙,结果逐字节一致(确定性);
- [ ] `docs/benchmarks.md` 记录:体素分辨率 vs 面数 vs 烘焙时长 vs 穿墙率(手工测试)。

**降级方案:** Surface Nets 出问题 → 退到二值场直接 Marching Cubes;仍不行 → 体素 AABB 逐块合并生成方块网格(丑但绝对可用)。

### 5.3 模块 M3:近似动态光照(核心模块二、博客主题)

**目标:** 手电筒等动态光源在扫描场景上产生**近似正确的阴影与明暗**,无需重训练 splat。

**原理(必须在博客中诚实说明这是近似)**

splat 外观是训练时烘焙的,不响应新光照。用 M1 的代理网格充当"光照替代几何":代理网格参与场景的阴影投射(shadow caster),splat 像素渲染时按其**背后代理几何的深度与法线**采样阴影/光照进行调制。近似误差来源:代理与 splat 表面的偏差 ε(体素半宽)、薄结构的缺失——这是博客的误差分析素材。

**实现路径(按优先级)**

- **路径 A(推荐):双 pass 深度调制**
  1. `ProxyDepthPass`(ScriptableRenderPass,RenderGraph):把代理网格以 `ColorMask 0` + `ZWrite On` 渲染到单独深度目标(proxy depth);代理不投影阴影(避免双重)。
  2. splat 渲染后追加 `ShadowModulationPass`:读取场景颜色 + 主光源 shadow map + proxy depth,对 splat 覆盖的像素按代理深度判定遮挡,乘以阴影衰减系数;非阴影区做轻微 N·L 调制(法线取自代理深度重建)。
  3. 需要修改/扩展 splat 着色器或以全屏 pass 后处理 splat 区域(依据深度差判定哪些像素属于 splat:场景深度 vs splat 写入深度——注意 splat 默认不写深度,需开启 Stochastic 深度写入模式辅助区分)。
- **路径 B(降级):着色器内直采**
  Fork Aras 的 splat shader,在混合前采样 URP 主光源阴影(`SampleShadowmap`),世界位置即 splat position,深度偏移按 chunk bias 调整。实现快、但代理与 splat 位置偏差会造成阴影"漂移"。
- **路径 C(保底):法线调制**
  不用 shadow map,仅用代理网格法线做 N·L 方向光明暗调制 + 手电筒距离衰减。效果弱但零风险。

**参数:** 光照调制强度、深度偏移 bias(全局 + 逐 chunk)、调制作用半径(避免远景全屏调制开销)。

**验收标准**

- [ ] 手电筒扫过扫描墙面/地面,出现随光源移动的近似阴影,肉眼判定"可信";
- [ ] 开启/关闭调制整帧耗时差 ≤1ms(RTX 级,1080p);
- [ ] `docs/blog-draft.md` 完成:原理、实现路径对比(A/B/C)、误差分析、截图。

**降级顺序:** A 失败( RenderGraph 兼容问题)→ B;B 阴影漂移不可接受 → C。**任何路径都要在代码注释与博客中标注近似性质,不冒充"真实阴影"。**

### 5.4 模块 M4:分块流送与剔除 + 性能面板

**目标:** 大场景按相机距离分块加载/卸载;基于代理做遮挡剔除;提供运行时性能面板。

**实现要点**

1. **Chunk 流送**:复用 UnityGaussianSplatting 的 chunk 结构(每 chunk 有 AABB):按相机距离分级(近=完整渲染/远=降 SH 或剔除);卸载的 chunk 释放对应 GPU buffer(注意资产级 buffer 与 chunk 子集的关系,如资产不支持子集卸载,则按资产整体流送,chunk 级只做剔除)。
2. **遮挡剔除**:代理 chunk AABB 视锥剔除后有剩余时,用上一帧深度缓冲或代理 SDF 做保守遮挡测试(简化实现可接受:以"相机到 chunk 中心连线是否穿过已确认实体体素"为启发式)。
3. **性能面板**(IMGUI,`PerfPanel` 组件):splat 总数/可见数、排序 ms、光照 ms、fence 等待、fps、显存估算;数据同步写 `docs/benchmarks.md`。

**验收标准**

- [ ] 3 个场景连续漫游 5 分钟,无可见"突然弹出"(流送距离 > 弹出距离);
- [ ] 性能面板与 Profiler 读数一致(误差 <10%);
- [ ] 开启遮挡剔除后远处被建筑遮挡的 chunk 渲染耗时显著下降(记录数据)。

**降级方案:** chunk 级流送复杂 → 资产级流送(整场景资产多文件时逐个加载/卸载);遮挡剔除做不保守 → 只做视锥 + 距离降级。

## 10. 工程规范

- **代码风格:** C# 标准;命名空间 `Splat2Play.*`;类名 PascalCase;注释中文,解释"为什么"而非"是什么";shader/compute 放 Shaders/Compute 目录统一命名(`S2P_` 前缀)。
- **提交:** 中文提交信息,格式 `M<里程碑>: <做了什么>`;每个任务至少一个提交;里程碑完成打 tag(`M0`–`M4`)。
- **大文件:** `*.ply/*.spz/*.sog/*.ksplat` 不进 git;演示视频素材不进 git(发布用 GitHub Release 或外部)。
- **测试:** M1 的体素化/填充必须有 EditMode 单元测试(已知小场景的预期输出);UI 与 AI 行为用 PlayMode 冒烟测试。
- **文档同步:** 每完成一个任务,更新对应文档(ROADMAP 勾选、benchmarks 追加);文档与代码不同步视为任务未完成。

### 11.3 AI 执行者常见陷阱清单(每会话结束前自查)

1. **编造 Unity API**(尤其 RenderGraph/NavMeshSurface 的具体签名)——必须对照文档或现有代码;
2. 忘记 URP 与内置管线的 API 差异(`CommandBuffer.Blit` 在 URP 已废弃等);
3. 把 `Library/`、`Logs/`、扫描 `*.ply` 加入 git(gitignore 已挡,勿用 `git add -f`);
4. 在 `Runtime/` 程序集里引用 `UnityEditor` API(必须隔离到 `Editor/`);
5. 忽略确定性:烘焙算法含随机性会导致同参数结果不一致(§5.1 验收项);
6. GPU 侧改动忘记同步回读/bounds 更新(§2.2 关键性质);
7. 过早优化:先按规格实现并测量,不要凭感觉重写算法。

### 11.4 验收流程(每个任务完成后)

人类(或主控 AI)执行:① 编译零警告零报错 → ② 跑对应单元/冒烟测试 → ③ 对照该任务验收标准逐条勾选 → ④ `docs/benchmarks.md`/ROADMAP 已同步 → ⑤ 提交信息符合规范 → 通过则合入,否则退回并附具体失败项。
